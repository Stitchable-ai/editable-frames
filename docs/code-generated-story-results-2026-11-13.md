# Interaction acceptance and code-generated story films — 2026-11-13

> **2026-11-14 follow-up:** the original Fable worker resumed, repaired camera/gaze state dependence and completed the film. Independent checks reproduce 1,152 frames, 228 new seek samples and all 12 controls; a three-frame CLI edit/undo specimen also passes. Earlier unfinished-draft failures below are historical. Acting/contact, native integration and style reuse remain open. See [current evidence](hybrid-gap-closure-2026-11-14.md).

## Decisions from the latest outputs

The user accepts the visual direction of the full-pickup and two-person handoff outputs and prefers the Fable 5.2 story film as closer to the supplied fantasy-game references. These are **user visual acceptance and preference**, not independent certification of every frame, exact product fidelity, or a completed Fable review. The two model implementations are one creative exercise, with different refinement histories; they are not a general model benchmark.

Keep two distinct production routes, selected by the required representation and editability:

| Need | Selected route | What remains editable | Evidence / boundary |
|---|---|---|---|
| Realistic people handling a product or exchanging it | Stage the scene → approved start image plus identity/product references → jointly generate the interacting subjects and room → review → EditableFrames finishing | Staging before generation; accepted footage selection/timing/crop/grade and separate titles/captions afterward | Pickup and completed transfer now have user-accepted examples. Physical performance and product pixels are baked; repeatability and exact identity/branding remain open. |
| Stylized characters acting in an authored world | Code builds the set, rigs, action, cameras, lights and renderer; export directly | Authored geometry, rigs, animation and look in source; selected parameters via controls | Two 48-second fantasy RPG films rendered. Fable's direction is preferred, but its draft fails one seek check and requires refinement. Not generic automatic character animation. |
| Realistic interaction within an otherwise editable story | Use an approved authored shot/snapshot as generation input, then return the accepted clip to the edit | Code shots stay editable; generated sections have the same baked boundary as above | Proposed shot-level combination; this story exercise did not test such a round trip. Do not claim that model video preserves exact meshes or camera motion. |

The earlier interaction rule applies to **independently assembled realistic plates**. It must not become a ban on code-authored character stories. A shared authored rig and choreography can represent an interaction; independent masks cannot invent it. Nor does stylization excuse intersecting hands, incoherent eyelines, or unsupported props.

## What Fable actually used

Both entries use **Three.js raster rendering in the current EditableFrames `defineRenderer` / `mountRenderer` contract**, exported locally through browser capture and FFmpeg. No diffusion-generated frames, external character asset pack, path tracer, NVIDIA-only runtime or paid generation call was used for these films. The difference is authored assets, staging and rendering choices, not a different foundational framework.

| Area | Fable implementation observed in source | Why it fits the references better / remaining limitation |
|---|---|---|
| Character construction | Lofted heads and bodies, character-specific proportions, separate noses/ears/hair, articulated segmented limbs and five-finger hands. Canvas-painted face textures include lids, brows, pupils, mouth states and emissive eyes. | Narrower faces and controlled facial detail read closer to the reference game art. This is procedural geometry and a scene-specific rig, not a learned human reconstruction or a production facial rig. |
| Materials | Seeded, low-resolution stone, wood, cloth, leather and skin texture functions; nearest-neighbor magnification with mipmapped minification. Humanoids use Lambert materials. | Local wear, varied stone courses, planks and painted features provide more surface detail. Physically based materials alone do not guarantee a better stylized image; Astra used standard materials yet its asset forms were more primitive. |
| Acting | Two-bone arm IK, gaze targets, walk/sit/gesture poses, a deforming dragon spine and wings, speech-envelope-driven animation with limited facial states. | More purposeful action than small idle oscillations. IK positions joints; it does not verify grasp, reach, collisions or force. Speech-envelope animation is not phoneme-level lip sync. |
| Camera and sets | Fifteen shots rather than Astra's eight; a medieval lane and a furnished tavern; approach, reaction, over-table, detail and ensemble shots. | Greater spatial context, shot variety and first-person framing. The doorway transition and handoff detail still need refinement. |
| Lighting and finish | Local torches, ember, window/fill and chandelier lights; HDR beauty pass at twice the output dimensions, object-ID/depth contour pass, half-resolution bloom, tone mapping, grade, vignette and grain. | Local light and depth-aware contours make a coherent game-art look. The large bloom/highlights also obscure detail in parts of the draft; adding effects is not automatically a quality improvement. |
| Framework | Explicit frame clock and editable light/look/camera/title/subtitle properties, with separate local TTS/audio preparation. | Source remains authorable and selected controls redraw the scene. This does not make every performance or audio edit automatically available in a panel. |

These are source-backed mechanisms and plausible contributors to the user preference, **not isolated causal tests**. No ablation has established which individual technique explains how much of the difference. The preferred direction is a reusable authoring approach, not a requirement to reproduce Fable's bugs or every shader.

## Actual result and acceptance

- **Astra:** 48.000 seconds, 720×1280, 24 fps, 1,152 decoded frames, voiced/subtitled. Three sampled repeat seeks matched exactly in the tested browser; a light-control edit changed the scene. Faces/hands remain puppet-like, material and architectural variety are limited, and jaw movement is approximate.
- **Fable 5.2:** authored the scene, soundtrack and 15-shot timeline, then hit its provider usage limit during visual refinement. The parent exported that saved source unchanged; hashes before/after confirm preservation. Both full video and original source are retained. The output is a **recovered unfinished draft**, not Fable's final approved delivery.
- **Recovered Fable export:** 48.000 seconds, 720×1280, 24 fps, 1,152 frames decoded without video errors. Light-control edit changed the render. A generic browser resource 404 was retained; its URL was not established, so it is not silently dismissed as a confirmed favicon request.
- **Seek defect:** frames 228 and 768 repeated exactly, but frame 960 changed 183,794 pixels; mean channel difference 7.128/255, maximum 238. The dragon's head direction visibly changes. The `better` shot reads the previous camera position for its gaze before setting the current camera, a likely cause from source inspection; a fix has not yet been verified. Successful sequential export does not pass random-access authoring.
- **Audio recovery:** initial decoded AAC peak was 1.372. The parent applied gain 0.5 at output while copying video unchanged; delivered peak measured 0.737. The original audio export is retained. This avoids the measured output overshoot but cannot undo distortion already present in the mix.
- **Visual limits:** rigid joints, sparse facial animation, awkward/oversized hand contact, strong light/bloom and the doorway transition. Fifteen shot stills and a 1 fps decoded sheet were inspected; there is no claim of normal-speed playback or exhaustive visual inspection of all 1,152 frames by the reviewer.

The user prefers Fable's **visual direction**. Neither film reaches the reference's character finish; a general production-ready or deterministic story engine is not yet demonstrated. References supplied art direction; their screenshot pixels were not used as finished scene backgrounds. Preserve reference rights/provenance before redistributing any supplied images.

## Story track: extend beyond the dungeon without constraining the core

This is a new authored-story exercise, separate from **feature item 6 (camera solve)** and **feature item 13 (world reconstruction into splats/meshes)**. Code-generated geometry and known cameras do not validate either deferred feature. Also keep it distinct from the existing “many versions from one take” journey numbered 6.

1. **ST1 — finish and stabilize this film.** Let Fable complete its own refinement when available. Correct the current-frame camera/gaze dependency and test random, repeated and reverse seeks across every shot and cut boundary; compare with sequential frames in the same renderer. Inspect normal/slow playback, all contact intervals, reach/support/release, camera-wall clipping and gaze. Repair highlight loss and audio gain; retain original versus corrected versions and explicit authorship. Verify each advertised control in both preview and export. No model call or wall-clock state inside frame rendering.
2. **ST2 — extract optional reusable authoring modules.** Separate character shape/face/rig, props and set dressing, action targets/contacts, shot/camera track, light track, material/contour/post look and dialogue/subtitle timing. Give selected controls stable IDs and source bindings; keep arbitrary source code and replacement renderers possible. Do not embed a mandatory fantasy vocabulary, actor taxonomy or model provider into the core. Existing film scripts are prototypes, not a shipped animation package.
3. **ST3 — test style transfer through code, not only palette changes.** Produce three additional short studies, for example a science-fiction repair shop, a sunny cel-shaded village and a clay/toy workshop. Use a common walk → dialogue → shared-prop action and camera brief while changing silhouettes, facial design, surface detail, set construction, light response and contour/post treatment. Retain the full editable sources and exact settings. Each style must pass its own whole-shot visual review; portability beyond the fantasy study is currently unproven. No new hosted spending is implied.
4. **ST4 — test practical reuse and host delivery.** Reuse an approved actor across shots and changes in framing, light, costume and dialogue; check identity, silhouettes and contact after edits. Regenerate local speech/alignment when dialogue changes rather than retaining stale audio. Bind source, assets and audio to project revisions and test save/reload, undo/redo and export parity in the host before claiming an integrated story workflow. Measure preview, capture time and peak memory on actual additional desktop/laptop machines; this Mac run establishes no performance floor for ordinary computers.

Style is an open combination of authorable geometry, textures, rigs, cameras and lights, not a fixed list of “dungeon / office / cool” presets. Presets may be convenient starting points. Cross-style reuse and a useful agent authoring workflow must be earned by ST3/ST4, not inferred from parameter exposure alone.

## Interaction work that remains

The accepted pickup/handoff samples validate the selected staged joint-generation direction sufficiently to proceed with host implementation. Prioritize frozen scene-set capture, ordered reference roles/hashes, durable submission receipts, failed/ambiguous-job handling, actual decoded timing and accepted-take import; keep provider work outside rendering. Repeat the tests with both people identity-referenced and with difficult contact/occlusion before claiming broader reliability. Exact product geometry/print, multi-angle consistency, object–object collisions and animal interactions remain separate acceptance gates. The detailed [staged-generation report](staged-generation-results-2026-11-13.md) retains the observed action beats, estimates and limits.
